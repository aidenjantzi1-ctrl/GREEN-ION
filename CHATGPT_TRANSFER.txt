SECTION 2 — MISSION AND PROJECT CONTEXT
================================================================

GOAL
Build a reliable, reusable electronics payload to fly inside different model
rockets (initially Green Eggs and the two-stage So Long), measure real flight
parameters, log locally, transmit selected live information for recovery, and
analyze flights from a phone/iPad and Windows laptop.

CURRENT ROCKET USE
- Estes Green Eggs: first/main payload test and recovery-friendly flights.
- Estes Pro Series II So Long: separate two-stage rocket. Assess payload
  envelope, weight, center of gravity, recovery separation and secure
  retention individually; compatibility is NOT guaranteed by the software.
- Event: ROCstock, Lucerne Valley, with Rolling Robots involvement.
- Follow manufacturer staging/recovery guidance and the range safety officer.
- Reuse the same GREEN ION electronics across rockets when physically safe.
- The payload should function independently of internet and a live phone link.

ENGINEERING PHILOSOPHY
1. Never lose the primary flight log due to optional sensors, radio, UI,
   printing, network requests, graphs or convenience features.
2. Separate development/demo mode from actual sensor and flight evidence.
3. Prevent operations that could interrupt an active flight.
4. Distinguish not tested, inconclusive, failed, and passed.
5. Keep the code useful for more than one rocket.
6. Keep setup easy enough to follow with exact wiring, commands and steps.
7. Every code release needs reproducible tests and artifact provenance.

SECTION 4 — HARDWARE AND CONNECTIONS (VERIFY EXACT BOARDS)
================================================================

IN ROCKET
- Adafruit Feather ESP32 V2 main MCU.
- BMP388 barometer.
- LSM6DSO32 IMU (configured for ±32 g, accelerometer + gyro).
- PA1010D GPS over I2C.
- microSD card/breakout.
- Optional Adafruit RFM95W 900/915 MHz LoRa transmitter with antenna.
- Protected one-cell LiPo battery.
- Optional suitable active buzzer driven THROUGH a transistor circuit.
- Properly secured, insulated payload sled, wiring and antenna.

FEATHER V2 PIN MAP (current source, confirm printed labels/datasheets)
- I2C SDA GPIO22; SCL GPIO20.
- SPI SCK GPIO5; MOSI GPIO19; MISO GPIO21.
- microSD chip select GPIO33.
- RFM95W radio chip select GPIO27, reset GPIO15, DIO0 GPIO32.
- Buzzer-driver input GPIO14 (NOT a direct buzzer GPIO connection).
- Feather battery monitor GPIO35.
- Controlled STEMMA QT/I2C power via NEOPIXEL_I2C_POWER.
- Common GND required.

GROUND
- Arduino Uno R3 + a compatible level-shifted/regulator-equipped Adafruit
  RFM95W BREAKOUT, NOT a bare 3.3 V RFM95W connected to Uno 5 V logic.
- For the documented appropriate breakout: Uno 5V→VIN; GND→GND;
  D13→SCK, D11→MOSI, D12→MISO, D4→CS, D2→RST, D3→DIO0.
- Appropriate radio antennas required before ANY transmissions.
- Uno USB data cable to Windows computer; close Arduino Serial Monitor
  before Python opens that COM port.

CAUTION
- Different manufacturers' VIN/VCC labels can mean different requirements.
- Verify exact part numbers, board revisions, battery JST polarity and
  supply voltage with board documentation and a multimeter BEFORE soldering.
- A bare RFM95W needs 3.3 V power and level shifting from Uno signals.
- Do not solder or hot-plug LiPo while powered.
- Power components and soldered wiring must be mechanically secure enough
  for launch loads; loose breadboard jumper wires are not flight mounting.
- An antenna and batteries must not snag or interfere with recovery.
- Do not connect electrical staging or deployment controls to GREEN ION.
- See README's 'SOLDERING AND WIRING' section for full detail.

SECTION 5 — CURRENT DATA FLOW AND FEATURES
================================================================

FEATHER RECORDER
- Target sampling rate: 50 Hz.
- Three-second fixed prelaunch buffer (150 primary samples).
- Stationary pressure baseline calibration and automatic launch watching.
- Pressure/barometric data as primary RKT4 v2 binary log.
- Synchronized IMU/GPS data as companion sensor log.
- Periodic flushing and alternating checkpoint/recovery evidence.
- Landing-based automatic finalization and metadata.
- Data should continue recording if Wi-Fi or radio connection disappears.
- Sample timing, sensor faults and storage health are tracked.
- Watcher must NOT control actual engines, ignition or parachutes.

FLIGHT FILES
- /V12D###.BIN = primary RKT4 v2 flight log.
- /V12D###.SEN = matching full-resolution IMU/GPS companion.
- /V12D###.TXT = metadata.
- Recovery journal/report files may also exist.
- NEVER delete or overwrite original flight files during a home test.
- Preserve RKT4 v2 compatibility and companion binding semantics.

WIRELESS TELEMETRY
- Feather and Uno share a 70-byte CRC-protected telemetry v2 packet.
- Example fields: sequence, pressure, barometric and GPS altitude,
  acceleration axes/magnitude, gyro axes, speed, battery, GPS freshness,
  position, satellite count, status and health.
- Target telemetry cadence is roughly 1 Hz.
- Provisional LoRa settings: 920.5 MHz, 125 kHz bandwidth, SF7,
  coding rate 4/5 and 13 dBm, sourced from shared radio config.
- Frequency/channel use must be coordinated with ROC and comply with
  applicable radio regulations; frequency in range is not proof of legality.
- GPS last-known coordinates must be labeled stale; never imply a current
  fix without evidence.

HOME TESTING
- Testing tab includes a stepwise home verification wizard.
- Checks actual battery/pressure/calibration, IMU, GPS, temporary SD test,
  five LoRa bench transmissions, manually confirmed receiver reception,
  manual LiPo-only operation and secure mounting review.
- 30-second genuine 50 Hz sensor recording to reserved /GIHOME.BIN.
- Verifies RKT4 header, record structure/count, timing, valid records,
  missed periods and temp cleanup. Wi-Fi disappearance is reported
  separately, not assumed.
- Temporary home mode disables launch watch until explicit end/recalibrate.
- Test report JSON includes passed/failed/inconclusive/not-verified steps.
- DO NOT call this an actual flight simulation or full safety certification.
- Some state/confirmations currently reside in browser UI; future design
  should improve device-side persistence and recovery after disconnections.

OTA / ROLLBACK
- V12 phone dashboard includes guarded OTA and alternate-slot rollback.
- Bench maintenance stops launch watching and blocks unsafe operations.
- Upload correct Feather .ino.bin from successful CI, not merged images,
  partitions, bootloader or Uno .hex.
- Needs valid OTA partition layout and sufficient battery/stable power.
- OTA and rollback still need real power-interruption/hardware validation.
- Never perform OTA at a launch pad or while flight data is open.

PHONE AND COMPUTER
- Feather provides its own GREEN-ION-V12 local Wi-Fi dashboard at
  http://192.168.4.1 (read current README for configuration).
- Windows ground station via Arduino Uno serial at 115200 baud.
- Identify COM port in Device Manager; pyserial is required.
- CSV logs and last known coordinates shown on computer.
- Demo mode must be unmistakably marked and NEVER count as test evidence.
- Offline analysis and charting should preserve original files.

POST-IMPLEMENTATION HARDENING — HOME/LoRa/COMPUTER
================================================================

The main V12 six-feature suite described above is now implemented. Later
hardening requires newly started and completed IMU/GPS measurements within
the active home session before the Feather persists a PASS. It cancels the
launch watcher BEFORE SD cleanup/NVS writes; failures restart calibration.

The Windows ground station now exports mixed receiver-side radio bench events
and live telemetry with stable CSV columns, time-of-receipt and an additional
raw_packet_json field that preserves all original/future packet attributes.
Five transmit packets from the Feather alone are not proof of Uno reception.

Regression tests for these edge cases are in
tests/test_v12_six_upgrade_hardening.py. The full feature release checklist
is docs/V12_SIX_FEATURE_VALIDATION.md. Hardware and flight tests remain
unperformed unless the latest testing log contains actual measured evidence.
