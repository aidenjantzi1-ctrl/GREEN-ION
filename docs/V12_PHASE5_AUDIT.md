# Phase 5 Recovery software acceptance audit

The Recovery software workflow is implemented on `codex/green-ion-v12`. This audit covers software behavior under controlled telemetry and browser fixtures. It does **not** establish rocket position accuracy, real Wi-Fi reconnection, iPhone location permission, LoRa range, SD integrity after a flight, or launch readiness. Those physical checks are **NOT TESTED**.

| Requirement | Software evidence | Limit |
| --- | --- | --- |
| Rocket coordinate and confidence | The Ground Station retains the last valid GPS fix with receive time, age, source, firmware phase, fix quality and satellites. Descent and last-known coordinates are not labeled confirmed landing sites. Invalid or absent coordinates clear the displayed position and map link. | The receiver's reported fix quality and satellite count do not measure actual location error. |
| User position | Manual latitude/longitude validates geographic ranges. Browser geolocation requests permission only on explicit action, shows accuracy and observation time, marks old device positions stale, and tolerates temporary watch timeouts. User position stays in page memory. | Browser geolocation needs HTTPS or localhost. Plain HTTP from a laptop to an iPhone does not provide secure-context geolocation; Phase 7 must address secure mobile networking. Windows GPS accuracy is unverified. |
| Map and offline fallback | The offline relative rocket track stays available. The optional OpenStreetMap tile view renders accepted rocket trail plus separate rocket and user markers. On tile failure, coordinates, track, direct distance, bearing and connection state remain available. | Online tiles require internet; no satellite imagery provider or Google Maps API key is configured. |
| Distance and bearing | A spherical great-circle calculation produces straight-line distance and true bearing, including antimeridian cases. Metric/imperial selection is saved in the browser. No routes are generated. | Distance is to the last received coordinate, which may be old or before landing. |
| Google Maps | The button opens a coordinate search for a validated last rocket fix and is disabled by hiding when no valid coordinate exists. | It requires a usable browser/network; it sends the coordinate to Google only when opened. No paid embedded Google integration is used. |
| Communications and SD handoff | Recovery displays Feather Wi-Fi verification, LoRa packet age/RSSI, source and last position. A transition from noncurrent to current Feather Wi-Fi telemetry displays **Rocket Wi-Fi Reconnected** and enables the Analysis SD-inspection action. Analysis already provides list, raw download and validated RKT4 import. | A fixture exercised the state transition; a physical disconnected rocket/receiver was not tested. A live packet establishes a current telemetry connection, not SD health or flight file validity. |

Verification: `python3 -m unittest discover -s tests -p 'test_*.py' -q` (130 passed), `node tests/js/test_rkt4.mjs` (passed), JavaScript syntax check (passed), and `python3 tests/browser/recovery_smoke.py` (passed in 390-pixel Chromium). The browser smoke covers bench source return, valid/invalid/missing and stale rocket positions, GPS/radio loss and restoration, manual/device user position and temporary geolocation error recovery, distance and bearing including the antimeridian, metric/imperial units, Google coordinate link, separate map markers, tile failure fallback and no horizontal overflow. Browser inputs were fixtures; no physical hardware was attached.

Phase 6 flight analysis is the next software phase. Physical Recovery verification remains open for the local Windows, iPhone and rocket handover.
