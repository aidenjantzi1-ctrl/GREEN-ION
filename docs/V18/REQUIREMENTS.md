# GREEN ION V18 — Master requirements (planning, not release approval)

Status: proposed integration contract. Baseline: main at `17f517f275be7b52e3e71a1f2d656edbc65a08ea` (V17.0.1, merged PR #55). Owners: Primary firmware = `worker/v18-firmware`; Secondary Windows/offline app = `worker/v18-offline-app`; Integration Manager = `worker/v18-integration`; So Long Build Helper supplies physical documentation via integration PR. No cloud dependency, account or remote flight telemetry upload.

## Mission and boundaries
GREEN ION is an autonomous logger and recovery aid, not an ignition, staging, guidance, or deployment controller. Preserve original RKT4 v2 BIN layout, 50 Hz nominal acquisition, unique per-flight files, three-second prelaunch history where supported, journal/checkpoints, recovery and independent SD readback; verify complete BIN and metadata before claiming SAVED. Keep SD acquisition/writes completely independent of Wi-Fi, GPS, LoRa, serial UI and post-flight analysis. No optional peripheral may starve recorder work.

## Flight
- One large **PREPARE & ARM** action runs deterministic, sequential, firmware-owned real SD temporary write/read/verify/delete, storage and battery checks, BMP388/barometer and IMU checks, stationary calibration and detector self-test when required, final recheck, then autonomous watch. Show progress and concise actionable failures. Safe retry must not erase real flights, arm on stale state, duplicate commands, or create excessive test files.
- **Critical blockers:** failed/missing microSD, failed barometer/IMU, incomplete/unsafe recorder state, verified unsafe battery/storage. **Warnings, not blockers:** missing GPS fix, missing/broken/off LoRa. Never assert RF is working without physical evidence.
- Honest phase/event states: IDLE, PREPARING, ARMED, ASCENT/COAST/APOGEE/DESCENT (estimates with confidence), LANDED, SAVING, SAVED, ERROR. Ground UI must reflect firmware data with freshness/age and never fabricate successful save.
- Wi-Fi remains enabled before takeoff, switches off only after verified launch detection and a safe, recorder-priority transition, and returns after **independent** SD finalization + readback verification. Radio or Wi-Fi failure cannot prevent launch recording or landing save.
- FLY AGAIN only after distinct prior flight is safely saved. Fresh flight gets a new sequence/identity. User must be able to perform at least two sequential flights without reboot and without overwriting records.

## Four-tab, adaptive Windows/offline UI
**Flight, Recovery, Data, Settings** only as top-level V18 tabs. Flight prominently shows large phase-dependent action/status, battery and compact SD/GPS/LoRa badges; progressively disclose details and actionable errors. Recovery uses Arduino Uno plus separate LoRa receiver via USB Web Serial on Windows Chrome/Edge, explicit CONNECT RECEIVER, permission/reconnect instructions, protocol validation, GPS quality, last-known coordinates, packet age/signal and expanded diagnostics. Data manually imports BIN from SD/download, preserves exact originals, verifies and analyzes completely offline, supports history/search/reports and transparent confidence. Settings keeps configuration and advanced testing accessible without cluttering Flight. PWA/Windows package must work locally without cloud, account, subscription, internet or remote telemetry. Offline install/setup path must be documented and tested.

## Recovery/power
- GPS + LoRa used for recovery, not required for SD logging. Define radio packet version, CRC/length, sequence/age, coordinate validity, stale-state and compatible Uno serial output before implementations merge. No claim of working RF until antenna and receiver are physically validated.
- On landed/verified save enter configurable/default **five-minute recovery-transmission period** followed by battery-saving hibernation with **three-minute transmission intervals** when electrically and RF safe; physical wake button offers reliable safe wake/inspection. Define whether minute values are intervals/durations, and bounded radio TX behavior, in the firmware contract before final code approval. Recovery transmission must not risk SD save. Treat missing/invalid GPS as no-fix; retain last-known position marked stale.
- Retain 3.7 V **350 mAh** LiPo unless measured evidence supports replacement. Measure battery current in prepare, Wi-Fi, flight, recovery and sleep, brownouts and endurance; optimize aggressively without reducing recorder reliability. Charging capability is optional and must meet cell/charger safety; never assume an onboard charger or accessible port.
- Hardware: removable insulated secure sled for Estes Pro Series II So Long; measured fit, mass, CG/stability, stage coupling, recovery clearance, SD/USB access, strain relief, static pressure ports/placement, GPS visibility, antenna clearance/integrity and physical wake access. Verify official manual and approved motor combination; no staging-control functions in GREEN ION.

## Acceptance and release gates
Passing Python, native C++, JS/browser, Feather ESP32 V2 compile, Uno receiver compile, RKT4 backwards compatibility, LoRa packet/serial contract, Windows PWA/package, OTA rollback and two-flight/regression tests required for software candidate. Also simulate absent GPS/LoRa, radio drop, Wi-Fi transitions, interrupted SD write, power loss/reboot and filename collision. Hardware SD write/read/reboot, actual sensors/barometric baseline with properly vented bay, battery, radio antenna/RF range, recovery, physical mounting, loaded CG, stability and range safety remain UNVERIFIED until logged with evidence. No V18 release or deployment without explicit user approval. No deletion/closure of branches/PRs without explicit user approval. Historical Past_Versions and existing active build paths remain intact.
